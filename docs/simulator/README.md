# Simulator: stock versus MXZ Coordinator

Open the simulator at https://dkpnw.github.io/ha-mxz-coordinator/simulator/.

The page runs three invented rooms twice in your browser, stock heads on top and MXZ
Coordinator below, with one set of controls for both rows. It does not measure real
equipment, energy, comfort or noise.

## Run it from your own copy

Download or clone the repository and open `docs/simulator/index.html` in a browser.

## The rows and the controls

- **Stock** follows Mitsubishi's manual for heads on one outdoor unit: "the unit selected
  last goes into standby mode." It is not stock AUTO.
  [What stock AUTO does](../HOW-IT-WORKS.md#the-problem-in-detail).
- **MXZ Coordinator** runs the integration's own planner, timing and fan-hold code at its
  default settings, with Home Assistant 2025.11 timing. `mxz_row.py` feeds them the page's
  inputs and carries out the steps they return.

Each control sets the stock head directly. On the MXZ row, Set to is the room's target, Off
turns the room off and Heat or Cool turns it on, and the fan is set at the room's remote. A
speed the head already shows is held by turning the room's Fan auto off, since pressing it at
the remote changes nothing MXZ can see. MXZ reads a pick of the speed it set one step
earlier as its own write and puts back its own speed, as it does in Home Assistant. MXZ picks
heat or cool itself. A running head moves its room 1 °F a minute, and a room with no head
running drifts toward 76 °F (`verification/instance/invented_house/model.py`).

## What it leaves out

- Door and window pauses, Dry, freeze floors, overheat ceilings, hands-off rooms, Comfort
  priority, cloud heads, eco, season lockouts, dual setpoints, a room's own drift and the
  shared-mode select.
- Slow or unavailable heads, writes to several heads that interleave, and a command a newer
  plan replaces before it is sent.
- After MXZ takes a change made at a head mid-plan, the next plan here waits for the 10-second
  cooldown, so it can run up to 10 seconds later than in Home Assistant.
- Home Assistant finishes taking a change made at a head inside the next plan, because the
  room write waits on its plan and the follow-up plan starts first. No MXZ function says so,
  so this page follows that order by a rule of its own (`MxzRow._go_on`).

## Files

| File | What it is |
| --- | --- |
| `index.html`, `lab.css`, `lab.js` | The page. `lab.js` draws the rows and passes the controls to Python. |
| `world.py` | Both rows, the controls, the clock and the scenarios. |
| `mxz_row.py` | The MXZ row: the integration's functions over the invented heads. |
| `bundle.js` | Generated by `python3 tools/simulator_bundle.py`; rerun it after changing any of the page's Python. |

The page loads [Pyodide](https://pyodide.org/) 314.0.8 (about 10 MB) from cdn.jsdelivr.net
the first time.

## How it is checked

`tests/test_simulator.py` runs scripted scenarios on the real coordinator in Home Assistant and
on `mxz_row.py` from the bundle. After every step they must agree on the plan, each call to each
head, each wakeup and compute, and what MXZ saved at a restart. Where Home Assistant's number
of computes varies from run to run, they are compared on the calls and the end state. Broken
copies of `mxz_row.py` must fail, and so must a stale bundle.
